# tbl コマンド設計書

## 概要

PowerPointの表（`Table`シェイプ）・複数行テキストと、マトリックス状／
縦一列に並んだ複数のシェイプとを**相互に変換する** `tools tbl` サブコマンド。

- **表 → 四角形群（分解）**: セルごとに独立した四角形シェイプへ分解する
- **四角形群 → 表（合成）**: 選択したシェイプ群の座標からグリッド構造を
  推定し、新規の表オブジェクトへまとめる
- **複数行テキスト → 行ごとのシェイプ群（行分割）**: テキストボックスや
  テキストが埋め込まれた単一シェイプを、テキストの行ごとに独立した
  シェイプへ分割し、縦（行方向）に並べる

**どの変換を行うかは、実行時の選択状態から自動判定する**（後述）。
サブコマンドやオプションでの明示指定は不要で、常に`tools tbl`のみで
これらすべてに対応する。

解決したい問題:

- PowerPointの表オブジェクトは、セル単位で自由に移動・変形・アニメーション設定を
  したい場合に扱いにくい（表という1つのオブジェクトの中に閉じ込められている）。
  セルを独立したシェイプにできれば、後から個別に位置調整したり、
  一部のセルだけ強調したりする編集がしやすくなる（**分解**方向）
- 逆に、SVG取り込みやセルの手動合体などでバラバラなシェイプ群として
  存在している「表らしきもの」を、罫線・オートフィル・列幅変更などの
  表ならではの機能が使える正規の表オブジェクトに戻したい場面もある（**合成**方向）
- 複数行にまたがるテキストボックス（`ikko`で合体した後のシェイプなど）を、
  再び行ごとに独立したシェイプへ戻し、行単位で個別に位置調整・強調したい
  場面もある（**行分割**方向。`ikko`の逆変換に相当する）

サブコマンド名・単体エントリーポイント名ともに `tbl`
（`pyproject.toml` の `[project.scripts]` に `tbl = "tools.cli:run_as_subcommand"` を追加）。
短く叩きやすい名前を優先している（`vv`/`ikko`と同じ流儀）。

## `ikko`との関係

`ikko`（複数のテキストボックス→1つのテキストボックスに合体）と役割が近い。
`tbl`の「行分割」方向は`ikko`とちょうど逆の変換になる。

| コマンド | 対象 | 方向 |
| --- | --- | --- |
| `ikko` | テキストボックス | 複数 → 1つ（常に一方向） |
| `tbl` | 表・四角形シェイプ・複数行テキスト | 表 ⇔ 四角形群、複数行テキスト → 行ごとのシェイプ（**自動判定**） |

PowerPoint COM接続の取得処理は`outline`/`ikko`/`mokuji`と共通の
`common/powerpoint.py`を使う（`get_running_powerpoint()` /
`get_active_presentation()`）。無ければエラー終了する（`ikko`と同じ判断、
新規起動はしない）。

## 方向の自動判定

実行時の選択状態を見て、以下の優先順位で判定する。

1. **選択中のシェイプに表（`HasTable`が真）が1つ以上含まれる**
   → **分解方向**（表→四角形群）。対象範囲・詳細は「分解」の節を参照
2. **選択中のシェイプが表を含まず、2つ以上のシェイプが選択されている**
   → **合成方向**（四角形群→表）を試みる。詳細は「合成」の節を参照
3. **選択中のシェイプが表を含まず、ちょうど1つだけ選択されている**
   → そのシェイプが**テキストを持ち（`HasTextFrame`が真かつテキストが
   空でない）、かつ複数行（`\r`区切りで2行以上）ある場合**、
   **行分割方向**を試みる。詳細は「行分割」の節を参照。
   テキストがない、またはテキストはあるが単一行の場合は、
   何もしない。「変換対象がありません」と表示して正常終了する
   （分割・合成のいずれの意味も持たない選択のため、エラーにはしない）
4. **何も選択されていない場合**
   → **エラー終了する。** `ikko`とは異なり、`tbl`は分解・合成・行分割の
   いずれにも解釈しうるコマンドであり、未選択のまま自動的にどれかの
   方向を推測して実行するのは誤爆のリスクが高いと判断した。
   「対象を選択してから実行してください」と表示してエラー終了する

判定は`Application.ActiveWindow.Selection.Type`と`Selection.ShapeRange`の
中身を見て行う。

## 対象範囲（分解方向）

分解方向は、方向判定で「選択中のシェイプに表が1つ以上含まれる」場合にのみ
実行される（未選択の場合はそもそも分解方向に到達せずエラー終了する。
前述「方向の自動判定」を参照）。

- `Selection.ShapeRange`の中から、`Shape.HasTable`が真のものだけを対象にする
  （表以外のシェイプが混在して選択されていても、表以外は無視する。
  エラーにはしない）

### 複数の表を選択している場合の処理順序

**`Selection.ShapeRange`の並び順（選択した順番）で、1表ずつ順番に処理する。**
一括で並行処理するのではなく、表Aを分解→表Bを分解、という形で
1つずつ完了させてから次に進む（`AddShape`で作った四角形の座標計算や
罫線判定が表ごとに独立しているため、順序に依存する処理はないが、
実装・ログ出力を単純にするため逐次処理とする）。

- 選択されたシェイプに表が複数含まれる場合、それぞれについて
  「分解の処理内容」を1表ずつ適用する
- 対象となる表が0個の場合（選択中に表が1つも含まれない）はエラーにせず
  「対象になる表がありません」と表示して正常終了する

## 分解の処理内容

対象の表1つにつき、以下を行う。

1. `Table.Rows.Count` × `Table.Columns.Count`ぶんの`Cell`を走査する
2. 各セルについて、`Cell.Shape`から座標（`Left`/`Top`/`Width`/`Height`）・
   テキスト・フォント（名前・サイズ・太字・色・段落揃え）・塗りつぶし色・
   4辺の罫線情報を取得する
3. 列ごとの間隔（`gap_x`）・行ごとの間隔（`gap_y`）を、各列の`Width`・
   各行の`Height`の一定割合（既定5%）として計算する（後述「座標・サイズの
   引き継ぎと、セル間の間隔」を参照）
4. 間隔を加味した新しい`Left`・`Top`を、累積オフセットとして計算する
   （後述「座標の再計算」を参照）。`Width`・`Height`はセルの元の値のまま変更しない
5. `Slides.Shapes.AddShape(msoShapeRectangle, 新Left, 新Top, Width, Height)`で
   新規の四角形シェイプを1つ作成する
6. 取得した情報（テキスト・フォント・塗りつぶし・罫線）を新規シェイプに設定する（後述）
7. 全セル分の四角形を作り終えたら、**元の表シェイプを`Delete()`する**

変換後にできる四角形群に対して、グループ化や自動整列などの後処理は行わない。
**独立した四角形のまま放置する。** 利用者が必要に応じて選択・グループ化・
`ikko`での合体などを行う前提とする（単純さを優先する既存の設計方針に揃える）。

### 座標・サイズの引き継ぎと、セル間の間隔

`Cell.Shape.Width` / `Height`（セルの見た目のサイズ）はそのまま新規シェイプに使う。
実機検証済みで、セルごとの座標・サイズが表内の実際の位置と一致することを確認している
（3行2列の表で、各セルの`Left`/`Top`が列幅・行高の積み上げと一致した）。

**分解後は、セル同士を隣接させず、上下左右に間隔を空ける。** 表のままだと
セルの境界がぴったり接しているため、分解後もそのままだと見た目が表と
変わらず、個別に動かした際に隣接セルと衝突しやすい。間隔を空けることで、
分解後のシェイプであることが視覚的にも分かりやすくなる。

- **各四角形の`Width`・`Height`（セルサイズ自体）は変更しない。**
  間隔の分だけ四角形群全体の外接矩形が元の表より広がる
  （個々のセルを縮小して元の表サイズに収めることはしない）
- **間隔（マージン）は、列幅・行高に応じてセルサイズの一定割合として計算する。**
  既定は5%とする:

  ```text
  列間隔(gap_x) = 列の Width の一定割合（既定 5%）
  行間隔(gap_y) = 行の Height の一定割合（既定 5%）
  ```

  列によって幅が違う表では列ごとに`gap_x`が異なり、行によって高さが
  違う表では行ごとに`gap_y`が異なりうる（後述の座標計算を参照）。
  セルサイズに対する割合にする理由: 固定ピクセル（ポイント）値だと、
  小さいセルでは間隔が目立ちすぎ、大きいセルでは間隔が目立たなさすぎる
  という不釣り合いが生じるため、セルサイズに応じて自動的にバランスを取る
- 行方向（縦方向の間隔）と列方向（横方向の間隔）は**別々に計算する**。
  表全体のセルサイズが縦横で大きく異なる場合（例: 横長の表）に、
  同一の間隔だと不自然になりうるため

### 座標の再計算

各セルの新しい`Left`・`Top`は、**カーソル方式**で左上のセルから順に計算する
（実装・検証済みの式）。

```text
cursor_x = 表の元の Left
列 c = 0, 1, 2, ... の順に:
    cursor_x += gap_x[c]       # このセルの手前に、このセルの列の間隔ぶん空ける
    new_left[c] = cursor_x     # ここが列cの新しいLeft
    cursor_x += width[c]       # 次の列のために、このセルの幅ぶん進める
```

`Top`・行方向も同じ考え方で`gap_y`・`height`を使って計算する。

- **列0・行0（左上のセル）も、表の元の位置からそのまま
  `gap_x[0]`・`gap_y[0]`ぶんだけ右・下にずれた位置に配置される**
  （左上のセルだけ特別扱いで間隔なしにする、ということはしない。
  四角形群全体を均等に表の外側へ広げるのではなく、全セルに同じ規則を
  適用することで実装を単純にするため）
- 列・行が進むごとに、それまでの列幅・行高と間隔の累積により、
  後ろの列・行ほど元の位置からのずれ幅が大きくなる
- この式で、隣接する2つの四角形の間には常に後方のセルの`gap_x`
  （または`gap_y`）ぶんの隙間ができることを実際に計算で確認済み
  （列幅[100, 150, 120]、既定5%の例で、隣接間隔が期待通り
  7.5・6.0になることを検証した）

## 分解後の全体サイズ

四角形群全体の外接矩形は、元の表より**間隔の合計ぶんだけ大きくなる**
（各四角形の`Width`・`Height`自体は変更しないため）。元の表と同じ
外接矩形に収まるよう各セルを縮小することはしない。理由:

- セルサイズを縮小すると、文字がセルに対して相対的に大きくなり、
  はみ出しや折り返しが発生する可能性がある
- 「間隔を空けて見やすくする」という目的に対し、外接矩形のサイズを
  維持する制約は本質的でない

### テキスト・フォントの引き継ぎ

- `Cell.Shape.TextFrame.TextRange.Text`をそのまま新規シェイプに設定する
- フォント名・サイズ・太字・色・段落揃えも同様にコピーする
  （`ikko`と同じく`Font.Bold`は`0`/`-1`の整数、`Color.RGB`も整数で扱う）
- 複数段落を持つセル（改行を含むセル）の場合、`TextRange.Text`をそのまま
  コピーすれば段落構造も保持される（COM側は`Text`プロパティの読み書きで
  `\r`区切りの段落情報をそのまま往復できるため、変換は不要）

### 塗りつぶしの引き継ぎ

`Cell.Shape.Fill.ForeColor.RGB`と`Fill.Visible`を新規シェイプにコピーする。
セルの背景が「塗りつぶしなし」の場合は、新規シェイプも塗りつぶしなしにする。

### 罫線の引き継ぎ（制約あり）

**実機検証で判明した制約**: 通常の四角形シェイプ（`msoShapeRectangle`）が持つ
`Shape.Line`プロパティは四角形全体で1つしかなく、上下左右の4辺で
別々の太さ・色を設定することはできない。一方セル側は`Cell.Borders(1〜4)`
（上/左/下/右）でそれぞれ個別の罫線情報を持てるため、単純にコピーできない。

この制約への対処方針:

- **4辺の罫線（太さ・色・表示有無）がすべて同じ場合**は、その値をそのまま
  新規シェイプの`Line.Weight` / `Line.ForeColor.RGB` / `Line.Visible`に設定する
- **4辺のいずれかが異なる場合**は、**上辺（`Borders(1)`）の値を代表値として
  4辺すべてに適用**し、その旨を警告ログに出す
  （「セル(r,c)の罫線が辺ごとに異なるため、上辺の値で統一しました」）。
  厳密な4辺個別の罫線再現（別途の線オブジェクトを4本追加する等）は行わない。
  実装の単純さを優先し、複雑な罫線パターンは変換後に利用者が手動調整する前提とする

## 合成（四角形群 → 表）

選択した2つ以上のシェイプ（表を含まない場合）を、座標からグリッド構造を
推定して新規の表オブジェクトへまとめる。実機検証で、以下の一連の流れが
機能することを確認済み。

### グリッド構造の推定

1. 選択されたシェイプそれぞれの`Left`・`Top`を取得する
2. **`Left`の値を許容誤差でまとめてクラスタリングし、列の集合とする。
   `Top`についても同様に行い、行の集合とする。**
   `ikko`の`LEFT_TOLERANCE`と同じ考え方で、既定の許容誤差は1.0ポイントとする
   （わずかな配置のズレを列・行の違いとして誤判定しないため）
3. クラスタリングした列数・行数から、行数×列数のグリッドを構成する
4. 各シェイプを、`Left`・`Top`が属する列・行の交点（グリッド位置）に割り当てる

**列・行間の間隔（隣接シェイプ同士の隙間）は均等であることを前提にしない。**
`Left`・`Top`の値そのものをクラスタリングして列・行を判定する方式のため、
シェイプ同士の間隔が均等かどうかは判定に影響しない
（前述「分解」の間隔付き四角形群を選択した場合はもちろん、隣接間隔が
列によって・行によってバラバラな配置でも、各列・各行の`Left`・`Top`が
それぞれ一つの値付近に集まってさえいれば、正しくグリッドとして認識できる）。

**同じグリッド位置に複数のシェイプが重複して割り当てられた場合はエラーとする**
（「同じセル位置に複数のシェイプが重なっています」と表示して変換を中止する。
中途半端な表ができるより、利用者に選択をやり直してもらう方が安全なため）。

### 歯抜けの扱い

**グリッドの一部にシェイプが存在しない（歯抜けの）場合でも、変換を中止せず
可能な限り推定して変換を試みる。** 歯抜けのグリッド位置は、新規の表では
**空セル**として扱う（テキスト・書式なしのセルとして残す）。

- 完全な長方形グリッドを要求すると、少し崩れた配置（意図的に一部のセルを
  結合・削除して作った表など）を一切合成できなくなり、機能として使いにくい
- 歯抜けの許容と、前述の「重複割り当てはエラー」は矛盾しない。歯抜けは
  「そこにシェイプがない」状態、重複は「同じ位置に2つある」状態であり、
  後者だけを事故として扱う

### 対象シェイプの形状

**四角形（`msoShapeRectangle`）に限定せず、選択されたシェイプの形状を問わない。**
テキストボックス・円・線などが混在していても、座標さえグリッドを作れれば
合成対象に含める。利用者が意図して選択した範囲をそのまま尊重する
（`tbl`による分解結果だけでなく、手作業で作った疑似的な表状の配置も
合成できるようにするため）。

### 選択が1つ以下の場合

**選択されたシェイプが1つ以下の場合は合成を行わない。** エラーにはせず、
「変換対象がありません」と表示して正常終了する（1つのシェイプからは
グリッドが作れず、合成する意味がないため）。

### 新規の表への変換

1. グリッド全体の外接矩形（各シェイプの`Left`・`Top`の最小値、
   `Left+Width`・`Top+Height`の最大値）を計算する
2. `Slides.Shapes.AddTable(NumRows, NumColumns, Left, Top, Width, Height)`で
   新規の表を作成する（外接矩形の位置・サイズをそのまま渡す）
3. 各グリッド位置に対応する元シェイプについて、テキスト・塗りつぶし色を
   新規表の該当セル（`Table.Cell(r, c).Shape`）にコピーする
   （分解方向と対称の処理。フォント・段落揃えも同様にコピーする）
4. **列幅・行高を、元のシェイプの`Width`・`Height`に合わせて個別に設定する。**
   `Table.Columns(c).Width`・`Table.Rows(r).Height`は表作成後に個別設定できる
   ことを実機検証済みで、不揃いな列幅・行高を持つ元の配置を再現できる
   （複数の元シェイプが同じ列・同じ行にある場合、代表値として最初に
   見つかったシェイプの`Width`・`Height`を使う）
5. 元のシェイプ群をすべて`Delete()`する

### 罫線について

合成方向では、元の四角形シェイプの`Line`プロパティ（1つのみ）を、
新規表の該当セルの4辺すべて（`Borders(1〜4)`）に同じ値で適用する。
分解方向の「4辺不一致で警告」のような分岐は不要
（四角形は元々1つの`Line`しか持たないため、4辺は必ず同一になる）。

## 行分割（複数行テキスト → 行ごとのシェイプ）

選択されたシェイプが1つだけで、かつテキストを持ち複数行（`ikko`の
逆変換に相当）の場合に行う。`ikko`が複数のテキストボックスを1つに
合体するのに対し、`tbl`の行分割は1つのテキストを複数のシェイプに
分割するちょうど逆の変換になる。

### 対象判定

- 選択されたシェイプが`HasTextFrame`を持ち、`TextFrame.TextRange.Text`が
  空でないこと
- そのテキストが`\r`区切りで**2行以上**あること
  （`TextRange.Lines().Count`で判定する。実機検証で
  `TextRange.Lines()`が段落コレクションとして機能し、`Count`が
  取得できることを確認済み。一方`TextRange.Paragraphs()`は
  コレクションとしての添字アクセスができなかったため、
  行の取得には`Lines(start, count)`を使う）
- 1行しかない場合、またはテキストがない場合は「変換対象がありません」と
  表示して正常終了する（前述「方向の自動判定」を参照）

### 行の取得

`TextRange.Lines()`で行数（`Count`）を取得し、`TextRange.Lines(i, 1)`
（`i`は1始まり）で1行ずつの`TextRange`を取得する。実機検証で、
この方式が各行のテキスト・フォント名・サイズを正しく返すことを確認済み
（`Lines(i, 1).Text`には行末の`\r`が含まれるため、末尾の`\r`を
トリムしてから使う）。

### 空行の扱い

**空行（テキストがない行）はスキップし、シェイプを作らない。**
元のテキストに意図的な空行区切りが含まれていた場合でも、
無駄な空のシェイプを増やさない。

### 分割後の配置

1. 元のシェイプの`Left`・`Width`はそのまま全ての新規シェイプに使う
   （横方向の位置・幅は変えない。縦方向にのみ並べるため）
2. 各行の高さは、**元のシェイプの`Height`を（空行を除いた）行数で
   均等に分割**した値を使う（実機検証済みの単純な方式。行ごとに
   フォントサイズが異なる場合の精緻な行送り計算は行わない）
3. 分解方向・合成方向と同じ考え方で、**行間にも間隔を空ける**。
   間隔（`gap_y`）は行高の一定割合（既定5%）とし、分解方向の
   「座標の再計算」と同じカーソル方式で、新しい`Top`を計算する
   （このケースは列方向の間隔は存在しないため`gap_x`は使わない）
4. 各行のテキスト・フォント名・サイズ・太字・色を、取得した`Lines(i, 1)`
   の情報からそれぞれの新規シェイプにコピーする
5. 全行分のシェイプを作り終えたら、**元のシェイプを`Delete()`する**

分割後にできるシェイプ群に対して、グループ化や自動整列などの後処理は
行わない。他の方向と同じく、独立したシェイプのまま放置する。

## エラー処理

共通:

- PowerPointが起動していない場合: 「PowerPointでプレゼンテーションを
  開いた状態で実行してください」と表示してエラー終了する（新規起動はしない）
- プレゼンテーションが開かれていない場合: 同様にエラー終了する
- **何も選択されていない場合**: 「対象を選択してから実行してください」と
  表示してエラー終了する（前述「方向の自動判定」の通り、未選択のまま
  分解・合成・行分割のいずれかを自動推測して実行することはしない）
- COM操作中に例外が発生した場合: 例外内容を含めたエラーメッセージで終了する。
  `Application.StartNewUndoEntry()`により、Ctrl+Z一回で開始前の状態に
  戻せる旨をメッセージに含める（後述）

分解方向:

- 対象になる表が0個の場合: エラーにせず「対象になる表がありません」と
  表示して正常終了する

合成方向:

- 選択されたシェイプが1つ以下の場合: エラーにせず
  「変換対象がありません」と表示して正常終了する
- グリッドの同じ位置に複数のシェイプが重複して割り当てられた場合:
  「同じセル位置に複数のシェイプが重なっています」と表示してエラー終了する
  （PowerPointの状態は変更しない。表の作成・元シェイプの削除は行わない）

行分割方向:

- 選択されたシェイプにテキストがない場合: エラーにせず
  「変換対象がありません」と表示して正常終了する
- 選択されたシェイプのテキストが単一行（改行なし）の場合: 同様に
  エラーにせず「変換対象がありません」と表示して正常終了する
  （分割すべき行が1つしかなく、変換の意味がないため）

## 元に戻す（Undo）

`ikko`と同じ理由で、**処理を開始する直前に`Application.StartNewUndoEntry()`を
必ず呼ぶ。** COM経由の変更はUndo履歴に入るが、境界を打たないと1回のCtrl+Zが
どこまで巻き戻るか制御できない（`ikko`の実機検証で、境界なしだとスライドの
追加自体まで巻き戻りスライドが消滅する事故を確認済み）。境界を打てば、
`tbl`による分解・合成・行分割処理全体が1回のUndoで正確に元の状態へ戻る。

## 出力・ログ

処理内容を`common/logging.py`経由でログに出す。

分解方向:

- 選択された表の個数と、処理順（選択順）
- 表ごとに、分解した行数×列数（何個の四角形になったか）
- 表ごとに、計算した`gap_x`/`gap_y`（列・行が複数ある場合は代表値、
  または最小・最大の範囲）
- 4辺の罫線が異なり代表値で統一したセルがあれば、その旨を警告ログに出す

合成方向:

- 推定したグリッドの行数×列数と、対象になったシェイプの個数
- 歯抜けのグリッド位置があれば、その個数を警告ログに出す

行分割方向:

- 分割前の行数（空行を除く）と、計算した`gap_y`
- 空行があれば、スキップした行数を警告ログに出す

完了時に標準出力へ1行のサマリを表示する
（例: `2個の表を分解しました（合計12個の四角形に）`、
`8個のシェイプを1個の表（4行2列）に合成しました`、
`1個のテキストを3行のシェイプに分割しました`）。

## セキュリティ方針との整合（CLAUDE.md）

- **COM操作は`pywin32`の公開APIのみ**を使う。生のWindowsフック・
  メモリ改ざん・プロセスインジェクションは行わない
- キー入力の自動送信・グローバルキーフックは行わない
- **常駐・バックグラウンド監視をしない。** 実行のたびに1回だけ
  対象を読んで変換し、終了する
- **外部通信は発生しない**（すべてローカルのPowerPointへのCOM操作のみ）
- 何を何個、どちらの方向に変換したかを`common/logging.py`経由で
  ログに出す

## テスト方針

判定・変換ロジックのうち、COM非依存にできる部分（罫線の代表値決定など）は
`common/`配下の純粋関数に切り出し、`tests/common/`でテストする。
`tests/processing/test_tbl.py`ではPowerPoint COMオブジェクトを`MagicMock`で
モックし、`AddShape`・`Delete`・`Cell`への呼び出しを検証する。

### 方向の自動判定のテスト

- 選択中に表（`HasTable`が真）が含まれるとき、分解方向が選ばれること
- 選択中に表が含まれず、シェイプが2つ以上選択されているとき、
  合成方向が選ばれること
- **選択中のシェイプがちょうど1つで、複数行のテキストを持つとき、
  行分割方向が選ばれること**
- **選択中のシェイプがちょうど1つで、テキストがない、または
  単一行のテキストしかないとき、どの方向も実行されず正常終了すること**
- **未選択のとき、エラー終了すること**（分解・合成・行分割のいずれも
  実行されないこと。誤爆防止の退行検知として重要）

### 分解方向の対象範囲判定（モック）

- `Selection.Type == 2`で表シェイプが選択されているとき、その表のみが
  対象になること
- 選択されたシェイプに表以外が混在していても、表以外は無視されること
- 選択された表が複数のとき、対象の表が0個のケース以外はすべて対象になること
- 対象の表が0個のとき、エラーではなく正常終了（メッセージ表示）すること

### 分解処理（モック）

- 対象の表の`Rows.Count × Columns.Count`と同じ回数だけ`AddShape`が
  呼ばれること
- **各セルの`Width`/`Height`が、間隔を加味しても変更されず
  元のセルサイズのまま新規シェイプに設定されること**
- 各セルのテキスト・フォント名・サイズ・太字・色が新規シェイプに
  コピーされること
- セルの塗りつぶし色・有無が新規シェイプにコピーされること
- 分解後、元の表シェイプに対して`Delete()`が呼ばれること
- **複数の表が対象のとき、表ごとに正しい個数の四角形が作られること**
- **複数の表が対象のとき、`Selection.ShapeRange`の並び順（選択した順番）で
  1表ずつ処理されること**（退行検知として重要。順不同や並行処理ではないこと）

### セル間の間隔付与（分解方向）

- **隣接する四角形同士の`Left`/`Top`の差が、元のセルの`Width`/`Height`
  よりも大きくなること**（間隔が実際に空いていることの担保）
- 列幅が異なる表で、列ごとに異なる`gap_x`が計算されること
  （列幅に対する一定割合として計算されること）
- 行高が異なる表で、行ごとに異なる`gap_y`が計算されること
- **列0・行0（左上のセル）の新しい`Left`/`Top`が、元の表の`Left`/`Top`
  そのものではなく、`gap_x`/`gap_y`ぶんだけ右・下にずれた位置になること**
- 列・行のインデックスが進むごとに、間隔の累積により後ろの列・行ほど
  ずれ幅が大きくなること
- 分解後の四角形群全体の外接矩形が、元の表より間隔の合計ぶん
  大きくなること（各セルの`Width`/`Height`は縮小されないこと）

### 罫線の引き継ぎ（分解方向）

- **4辺の罫線がすべて同じ場合**、その値がそのまま新規シェイプの
  `Line`に設定されること
- **4辺のいずれかが異なる場合**、上辺の値が代表値として4辺に適用され、
  警告ログが出ること

### グリッド推定（合成方向）

- 座標が完全なグリッドを作る複数シェイプから、正しい行数・列数が
  推定されること
- **`Left`/`Top`が許容誤差以内でわずかにずれているシェイプが、
  同じ列・行としてクラスタリングされること**
- **列間・行間の間隔が均等でない（列ごと・行ごとに間隔がバラバラな）
  配置でも、正しい行数・列数が推定されること**（`tbl`による分解結果
  そのままの選択を想定した退行検知として重要。間隔の均等性を
  前提にした実装になっていないことを確認する）
- **歯抜けのグリッド位置があっても変換が中止されず、その位置が
  空セルとして表に含まれること**
- **同じグリッド位置に複数のシェイプが割り当てられた場合、
  エラー終了し、表の作成・元シェイプの削除のいずれも行われないこと**
- 四角形以外の形状（テキストボックス等）が混在していても
  合成対象に含まれること

### 合成処理（モック）

- 推定した行数×列数で`AddTable`が呼ばれ、外接矩形の位置・サイズが
  渡されること
- 各元シェイプのテキスト・塗りつぶし色が、対応するグリッド位置の
  セルにコピーされること
- **列幅・行高が、元シェイプの`Width`/`Height`に合わせて
  個別に設定されること**（不揃いな列幅・行高が再現されること）
- 合成後、元のシェイプ群すべてに対して`Delete()`が呼ばれること

### 行分割処理（モック）

- 複数行（2行以上）のテキストを持つシェイプについて、
  空行を除いた行数と同じ回数だけ`AddTextbox`（または`AddShape`）が
  呼ばれること
- **各行の`Left`/`Width`が、元のシェイプの`Left`/`Width`と一致すること**
  （横方向の位置・幅が変わらないこと）
- 各行の高さが、元のシェイプの`Height`を（空行を除いた）行数で
  均等に分割した値になること
- **行間に`gap_y`（行高の一定割合、既定5%）ぶんの間隔が空くこと**
  （分解方向と同じカーソル方式の計算になっていること）
- 各行のテキスト・フォント名・サイズ・太字・色が、対応する
  `Lines(i, 1)`の情報から新規シェイプにコピーされること
- **空行はシェイプが作られずスキップされること**
- 分割後、元のシェイプに対して`Delete()`が呼ばれること
- 単一行（`Lines().Count == 1`）のとき、`AddTextbox`・`Delete()`の
  いずれも呼ばれず正常終了すること
- テキストがないシェイプが選択されたとき、同様に正常終了すること

### `StartNewUndoEntry`

- **処理開始前に`StartNewUndoEntry()`が呼ばれること**
  （分解・合成・行分割のいずれの方向でも、`ikko`と同じ理由の
  退行検知として重要）

### エラー処理のテスト

- PowerPointが起動していない場合、新規起動を試みずエラー終了すること
- プレゼンテーションが開かれていない場合にエラー終了すること
- **何も選択されていない場合、分解・合成・行分割のいずれも
  実行されずエラー終了すること**
- COM例外時に、Ctrl+Zで戻せる旨を含むエラーメッセージが出ること
- **選択されたシェイプが1つ以下（表を含まない）のとき、
  エラーにならず正常終了すること**
- **グリッド位置の重複が検出された場合、エラー終了し、
  `AddTable`・`Delete()`のいずれも呼ばれていないこと**
- **単一行テキストまたはテキストなしのシェイプが1つ選択された場合、
  エラーにならず正常終了すること**
