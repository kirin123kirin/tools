# seiretsu コマンド設計書

## 概要

選択した複数のシェイプを、**表オブジェクトへの変換を伴わずに**、
位置だけを整った格子状（マトリックス）に並べ直す `tools seiretsu` サブコマンド。

解決したい問題:

- SVGの取り込みや手作業の結果、本来は表のように整列しているべきシェイプ群が
  微妙にずれた位置に散らばってしまうことがある。表オブジェクトにする必要は
  なく（`tbl`の合成方向）、各シェイプを独立したシェイプのまま、見た目だけ
  整然と並べ直したい

サブコマンド名・単体エントリーポイント名ともに `seiretsu`
（`pyproject.toml` の `[project.scripts]` に `seiretsu = "tools.cli:run_as_subcommand"` を追加）。
「整列」から。短く叩きやすい名前を優先している（`vv`/`ikko`と同じ流儀）。

## `tbl`との違い

`tbl`の合成方向（四角形群→表）と入力の状況は似ているが、**出力がまったく異なる**。

| コマンド | 入力 | 出力 |
| --- | --- | --- |
| `tbl`（合成方向） | 座標がバラバラなシェイプ群 | 1つの表オブジェクト（元シェイプは削除） |
| `seiretsu` | 座標がバラバラなシェイプ群 | **同じ個数の独立したシェイプ**（位置のみ変更、削除も新規作成もしない） |

`seiretsu`は表への変換を一切行わない。各シェイプの形状・サイズ・テキスト・
書式はそのまま保持し、**`Left`/`Top`（位置）だけを書き換える**。

グリッド推定のロジック（座標クラスタリング）は`tbl`の合成方向と同じ
`common/table_shapes.py`の`estimate_grid()`をそのまま再利用する。

PowerPoint COM接続の取得処理は`outline`/`ikko`/`mokuji`/`tbl`と共通の
`common/powerpoint.py`を使う（`get_running_powerpoint()` /
`get_active_presentation()`）。無ければエラー終了する（新規起動はしない）。

## 対象範囲

- **選択中のシェイプのみ**を対象にする。`tbl`の合成方向と同じく、
  2つ以上選択されていることを前提とする
- **選択されたシェイプが1つ以下の場合はエラー終了する**。
  「対象を選択してから実行してください（2つ以上選択が必要です）」と表示する
  （未選択のまま実行して誤ってアクティブスライド全体を動かしてしまう
  事故を避けるため。`tbl`の合成方向とは異なり、`seiretsu`には「1つ選択時は
  別の動作」という分岐を持たないため、1つ以下は常にエラーとする）
- 選択に表（`HasTable`が真のシェイプ）が含まれていても、`seiretsu`は
  形状を区別せず単純に座標だけを見て処理する（`tbl`のような方向自動判定は
  行わない。`seiretsu`は常に「整列」の一択）

## グリッド構造の推定

`common/table_shapes.py`の`estimate_grid()`をそのまま使う。

1. 選択されたシェイプそれぞれの`Left`・`Top`を取得する
2. `Left`の値を許容誤差（既定1.0ポイント、`tbl`と同じ`GRID_TOLERANCE`）で
   クラスタリングして列の集合とし、`Top`についても同様に行を求める
3. 各シェイプを、`Left`・`Top`が属する列・行の交点（グリッド位置）に割り当てる
4. 同じグリッド位置に複数のシェイプが重複して割り当てられた場合はエラーとする
   （`tbl`と同じ`DuplicateGridPositionError`をそのまま使う）
5. グリッドの一部にシェイプが存在しない（歯抜けの）場合でも整列を中止せず、
   そのグリッド位置は空のまま残りのシェイプの整列を続行する

## セルサイズは列・行ごとに個別（`tbl`合成方向と同じ方式）

**セルサイズをグリッド全体で単一の値に統一することはしない。**
各列の幅・各行の高さは、**その列・行に属するシェイプの中で最大の
`Width`・`Height`**とする（`tbl`の合成方向でセル幅・行高を決める方式と同じ）。

```text
col_width[col]  = その列に属するシェイプの Width の最大値
row_height[row] = その行に属するシェイプの Height の最大値
```

### 単一セルサイズを採用しなかった理由

設計初期には「グリッド全体で単一のセルサイズ（全シェイプ中の最大値）に
揃える」方式を検討したが、これは元の配置に基づく間隔・位置と衝突し、
**隣接シェイプ同士が重なり合う**ことを計算で確認した（例: 元の配置が
密集していて列間の中心間隔が140ptしかないのに、1つだけ極端に大きい
シェイプ（幅300pt）が混在すると確実に隣の列へはみ出す）。

そこで**セルサイズを列・行ごとの個別最大値とする**方式に変更した。
これにより、各列・各行の幅・高さがその列・行内の最大シェイプに
一致するため、重なりの原理的な発生を防げる（後述「グリッド全体の
サイズ」の通り、この変更に伴い外接矩形を元の配置と一致させるという
要件も撤回した）。

## 整列後の位置計算（重心基準）

**各シェイプは、自分の`Width`・`Height`を保ったまま、シェイプの中心が
グリッドの格子中心に一致するように`Left`・`Top`を計算し直す。**

### 起点は揃えるが、全体サイズは外接矩形と一致させない

**整列後のグリッドの左上（`overall_left`・`overall_top`）は元の選択
シェイプ全体の外接矩形の左上に揃えるが、グリッド全体のサイズ
（右端・下端）は元の外接矩形とは一致させない。**

```text
overall_left = 選択シェイプの Left の最小値
overall_top  = 選択シェイプの Top の最小値
```

設計初期には「整列後の外接矩形を元の配置の外接矩形と完全に一致させる」
方式を検討したが、これは実装時に**列・行ごとの個別セルサイズ方式と
両立しない**ことが判明した。列・行のサイズ合計（`sum(col_width)` /
`sum(row_height)`）は、各列・各行に属するシェイプの実サイズから
決まる値であり、元の配置が密集していれば元の外接矩形より小さくなり、
疎らであれば大きくなる。外接矩形への一致を優先すると列幅・行高を
元のシェイプサイズから乖離させて拡大縮小する必要が生じ、
「各シェイプは元のサイズを保つ」という基本方針と矛盾するため、
**外接矩形の一致は要件から外し、単純に左上を起点として
列・行サイズの合計ぶんだけ右・下に広がる**方式に確定した。

### 各列・各行の中心座標（カーソル方式）

`common/table_shapes.py`の`compute_spaced_positions()`と同様の
カーソル方式で、列・行ごとのサイズ（`col_width[col]` / `row_height[row]`）
を順に積み上げて各列・各行の開始位置を求め、そこから中心座標を計算する。

```text
cursor_x = overall_left
col ごとに:
    col_start[col] = cursor_x
    grid_center_x[col] = cursor_x + col_width[col] / 2
    cursor_x += col_width[col]
```

`row`方向も同様に`row_height`を使って計算する。

- 列間・行間の間隔は空けない（隣接するセルはぴったり接する）。
  間隔を空けたい場合は`seiretsu`実行後に手動で余白を持たせるか、
  将来的な拡張とする

### 各シェイプの新しい位置

```text
new_left = grid_center_x[col] - shape.Width  / 2
new_top  = grid_center_y[row] - shape.Height / 2
```

`shape.Width`・`shape.Height`は元のシェイプのサイズをそのまま使う
（拡大・縮小はしない）。この計算式により、列・行のサイズが
その列・行内の最大シェイプに一致するため、**シェイプ同士が
重なることはない**（同じ列・行内の他のシェイプは、自分より
小さい`col_width`/`row_height`の中に収まる）。

## 変更しないもの

- シェイプの`Width`・`Height`（サイズ）
- シェイプの形状（四角形・角丸・楕円など）
- テキスト・フォント・塗りつぶし・罫線などの書式
- シェイプの個数・種類（表への変換や削除は行わない）

`seiretsu`が変更するのは**各シェイプの`Left`・`Top`のみ**である。

### 自動調整（AutoSize）への対応は不要

`nagasa`（サイズ統一コマンド）は、シェイプの「テキストに合わせて
図形のサイズを調整する」設定（`TextFrame.AutoSize`）が有効なままだと、
リサイズ後にテキストを編集した際にサイズが自動調整で巻き戻る事故が
実機で確認されたため、処理前に`AutoSize`を無効化する（`nagasa.md`参照）。

**`seiretsu`は`Width`・`Height`を一切変更しないため、この対策は不要である。**
実機検証で、`Left`・`Top`のみを変更した場合はテキストの再設定を行っても
`Width`・`Height`に影響が出ないことを確認済み（自動調整はシェイプの
サイズそのものに関わる操作にのみ反応し、位置の変更には反応しない）。

## エラー処理

- PowerPointが起動していない場合: 「PowerPointでプレゼンテーションを
  開いた状態で実行してください」と表示してエラー終了する（新規起動はしない）
- プレゼンテーションが開かれていない場合: 同様にエラー終了する
- 何も選択されていない、または選択されたシェイプが1つ以下の場合:
  「対象を選択してから実行してください（2つ以上選択が必要です）」と
  表示してエラー終了する
- グリッドの同じ位置に複数のシェイプが重複して割り当てられた場合:
  「同じセル位置に複数のシェイプが重なっています」と表示してエラー終了する
  （位置の書き換えは一切行わない）
- COM操作中に例外が発生した場合: 例外内容を含めたエラーメッセージで終了する。
  `Application.StartNewUndoEntry()`により、Ctrl+Z一回で開始前の状態に
  戻せる旨をメッセージに含める

## 元に戻す（Undo）

`ikko`・`tbl`と同じ理由で、**処理を開始する直前に
`Application.StartNewUndoEntry()`を必ず呼ぶ。** COM経由の変更はUndo履歴に
入るが、境界を打たないと1回のCtrl+Zがどこまで巻き戻るか制御できない
（`ikko`の実機検証で、境界なしだとスライドの追加自体まで巻き戻り
スライドが消滅する事故を確認済み）。境界を打てば、`seiretsu`による
整列処理全体が1回のUndoで正確に元の配置へ戻る。

## 出力・ログ

処理内容を`common/logging.py`経由でログに出す。

- 対象シェイプの個数と、推定したグリッドの行数×列数
- 各列の幅（`col_width`）・各行の高さ（`row_height`）
- 歯抜けのグリッド位置があれば、その個数を警告ログに出す

完了時に標準出力へ1行のサマリを表示する
（例: `9個のシェイプを3行3列に整列しました`）。

## セキュリティ方針との整合（CLAUDE.md）

- **COM操作は`pywin32`の公開APIのみ**を使う。生のWindowsフック・
  メモリ改ざん・プロセスインジェクションは行わない
- キー入力の自動送信・グローバルキーフックは行わない
- **常駐・バックグラウンド監視をしない。** 実行のたびに1回だけ
  対象を読んで整列し、終了する
- **外部通信は発生しない**（すべてローカルのPowerPointへのCOM操作のみ）
- 何個のシェイプを、何行何列に整列したかを`common/logging.py`経由で
  ログに出す

## テスト方針

グリッド推定・セルサイズ計算・重心配置の座標計算は、
`common/table_shapes.py`の既存関数（`estimate_grid`）を再利用する部分は
`tbl`側のテストで検証済みのため、`seiretsu`固有のロジック（列・行ごとの
セルサイズ計算、重心基準の位置計算）はCOM非依存の純粋関数として切り出し
`tests/common/`でテストする。`tests/processing/test_seiretsu.py`では
PowerPoint COMオブジェクトを`MagicMock`でモックする。

### 対象範囲の判定

- 選択されたシェイプが2つ以上のとき、それら全てが対象になること
- 選択されたシェイプが1つ以下のとき、エラー終了すること
- 何も選択されていないとき、エラー終了すること

### グリッド推定・セルサイズ

- 座標が完全なグリッドを作る複数シェイプから、正しい行数・列数が
  推定されること
- 列間・行間の間隔が均等でない配置でも、正しい行数・列数が推定されること
- 歯抜けのグリッド位置があっても整列が中止されず、他のシェイプの
  整列が続行されること
- 同じグリッド位置に複数のシェイプが割り当てられた場合、エラー終了し、
  いずれのシェイプの`Left`/`Top`も変更されていないこと
- **各列の幅（`col_width`）が、その列に属するシェイプ中の最大の
  `Width`になること**（行についても`row_height`で同様）
- **列・行によってサイズが異なるシェイプが混在する場合、列・行ごとに
  独立したセルサイズになること**（グリッド全体で単一のサイズに
  統一されないこと）

### 重心配置の計算

- **整列後の各シェイプの中心座標が、対応するグリッド位置の中心座標と
  一致すること**（`new_left + width/2` がグリッド中心のxと一致する等）
- **各シェイプの`Width`/`Height`が変更されないこと**（位置のみ変わること）
- **整列後の全シェイプの外接矩形の左上（最小Left・最小Top）が、
  元の選択シェイプ全体の外接矩形の左上と一致すること**
  （右端・下端は列・行サイズの合計で決まり、元の外接矩形と
  一致するとは限らない。左上のみが一致することを検証する）
- **サイズが異なる複数のシェイプ（例: 小さい四角形と、列内の他のどの
  シェイプよりも極端に大きい四角形）が混在していても、シェイプ同士が
  重ならないこと**（列・行ごとの個別セルサイズにより、大きいシェイプが
  属する列・行が自動的に広がるため。単一セルサイズ方式で発生していた
  重なりが起きないことの退行検知として重要）

### 変更されないものの確認

- シェイプの個数が処理前後で変わらないこと（削除・新規作成が
  発生しないこと）
- シェイプのテキスト・フォント・塗りつぶし・罫線が変更されないこと
- シェイプの形状（四角形・楕円等）が変更されないこと

### `StartNewUndoEntry`

- **処理開始前に`StartNewUndoEntry()`が呼ばれること**
  （`ikko`・`tbl`と同じ理由の退行検知として重要）

### エラー処理のテスト

- PowerPointが起動していない場合、新規起動を試みずエラー終了すること
- プレゼンテーションが開かれていない場合にエラー終了すること
- 選択されたシェイプが1つ以下のとき、エラー終了すること
- グリッド位置の重複が検出された場合、エラー終了し、いずれのシェイプの
  位置も変更されていないこと
- COM例外時に、Ctrl+Zで戻せる旨を含むエラーメッセージが出ること
