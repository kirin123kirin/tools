# clipmd コマンド設計書

## 概要

クリップボード上の **Markdown ↔ リッチテキスト** を相互変換する `tools clipmd` サブコマンド。

解決したい問題:

- MarkdownをOutlook/Wordに貼ると `## 見出し` や `**太字**` が装飾されずリテラルのまま残る
- WebページやWordからコピーした内容をエディタに貼ると、表・箇条書き・リンクがプレーンテキストに潰れる

サブコマンド名・単体エントリーポイント名ともに `clipmd`
（`pyproject.toml` の `[project.scripts]` に `clipmd = "tools.cli:run_as_subcommand"` を追加）。

## 変換方向は自動判別

引数なしで実行し、**クリップボードが保持している形式を見て変換の向きを決める**。

| クリップボードの状態 | 判定 | 変換 |
|---|---|---|
| `CF_HTML` がある | リッチテキストがコピーされている | HTML → Markdown |
| `CF_HTML` がなく `CF_UNICODETEXT` のみ | プレーンテキスト（=Markdownとみなす） | Markdown → HTML(+プレーンテキスト) |
| どちらもない | 変換対象なし | エラー終了 |

Windowsのクリップボードは複数形式を同時に保持するため、リッチテキストをコピーすると
`CF_HTML` と `CF_UNICODETEXT` の両方が入る。したがって**`CF_HTML` の有無が判定条件**になる。

- どちらの向きに変換したかを `common/logging.py` 経由でログに出す
  （何が起きたか分からないまま貼り付けて崩れるのを防ぐ）。

### 向きの明示指定

`--to-markdown` / `--to-rich` で自動判別を上書きできる。**オプション名は出力側の形式を表す**。

| オプション | 変換 | 用途 |
|---|---|---|
| `--to-markdown` | 入力をHTMLとみなし → Markdown | エディタに貼れる形にしたい |
| `--to-rich` | 入力をMarkdownとみなし → リッチテキスト | Outlook/Wordに装飾付きで貼りたい |

指定された向きに対して**期待する形式がクリップボードに無い場合**の挙動を以下に定める。

- `--to-markdown` 指定で `CF_HTML` が無い場合
  → `CF_UNICODETEXT` の内容を**HTMLソースとして解釈して**変換する
  （HTMLをテキストとしてコピーしてきた場合に対応するため）。
  `CF_UNICODETEXT` も無ければエラー終了。
- `--to-rich` 指定で `CF_HTML` がある場合
  → `CF_HTML` は無視し、**`CF_UNICODETEXT` の内容をMarkdownとして解釈して**変換する
  （リッチテキストをコピーした状態で `--to-rich` を指定するのは、
  装飾が落ちたプレーンテキスト側をMarkdownとして扱いたいケースと解釈する）。
- いずれの場合も、**自動判別と異なる解釈をしたことをログに出す**
  （オプションで上書きした結果どう解釈されたかが分かるようにする）。

## 出力

**変換結果はクリップボードに書き戻すのみ**でファイルは作らない。
その場で Ctrl+V して貼り付けられる状態にすることが目的なので、画像系コマンドの
`save_result()` 規約（`%TEMP%`に保存する等）は適用しない。

### Markdown → リッチテキストの場合

`CF_HTML` と `CF_UNICODETEXT` の**両方を同時にセットする**。

- `CF_HTML`: 変換後のHTML。Outlook/Word/Slackなどはこちらを読んで装飾付きで貼り付ける
- `CF_UNICODETEXT`: 元のMarkdownテキストをそのまま入れる
  （プレーンテキストしか受け付けないアプリに貼った場合、Markdownのまま残るのが最も無害）

`EmptyClipboard()` 後に `SetClipboardData()` を2回呼ぶ（1回の`OpenClipboard`セッション内で行う）。

### リッチテキスト → Markdownの場合

`CF_UNICODETEXT` のみをセットする（変換結果のMarkdownテキスト）。
`CF_HTML` はセットしない（Markdown記法のテキストをHTMLとして貼られると二重変換になるため）。

## CF_HTML の形式

`CF_HTML` は生のHTMLではなく、**独自ヘッダを持つ形式**である。フォーマットIDは標準定数ではなく
`RegisterClipboardFormat("HTML Format")` で動的に取得する（この環境では49353だったが、
値は保証されないため必ず実行時に取得する）。

### 読み込み時

ヘッダは以下のような行から始まる。

```text
Version:0.9
StartHTML:0000000097
EndHTML:0000000283
StartFragment:0000000131
EndFragment:0000000247
```

（桁数はアプリによって異なる。読み込み時は桁数を仮定せず整数としてパースする。
書き込み時は後述の通り10桁ゼロ埋めで統一する。）

- 各オフセットは**先頭からのバイト数**（文字数ではない）。UTF-8前提。
- 実際に貼り付けたい範囲は `StartFragment`〜`EndFragment`
  （`<!--StartFragment-->` / `<!--EndFragment-->` コメントで囲まれている）。
- 読み込みでは `StartFragment`/`EndFragment` を使って断片だけを取り出す。
  ヘッダのオフセットが壊れているアプリもあるため、
  **コメントマーカーでの検索を優先し、失敗したらオフセットにフォールバックする**。
- `pywin32` の `GetClipboardData(CF_HTML)` はバイト列かstrかがアプリ依存で揺れるため、
  bytes なら UTF-8 でデコードする分岐を入れる。

### 書き込み時

ヘッダのオフセットは**自分で計算して埋める**必要がある。
オフセットは固定幅（10進10桁ゼロ埋め）で書き、ヘッダ自身の長さが変わらないようにしてから
実際のバイト位置を計算する（長さが変われば位置がずれるため、桁数固定が前提）。

```text
Version:0.9
StartHTML:{StartHTMLの位置}
EndHTML:{EndHTMLの位置}
StartFragment:{StartFragmentの位置}
EndFragment:{EndFragmentの位置}
<html><body>
<!--StartFragment-->{変換したHTML}<!--EndFragment-->
</body></html>
```

- `SetClipboardData` に渡すのは UTF-8 のバイト列。
- 実装ではヘッダをプレースホルダ付きで組み立て → バイト長を測って各オフセットを確定 →
  最終的な文字列を作る、という2パス方式にする。

## 変換ライブラリ

| 方向 | ライブラリ |
|---|---|
| Markdown → HTML | `markdown-it-py`（CommonMark準拠、表などのプラグインが使える） |
| HTML → Markdown | `markdownify`（BeautifulSoupベース） |

### Markdown中の生HTMLの扱い

プリセットによって挙動が真逆になることを確認した（検証済み）。

| プリセット | `html`オプション | `<br>` の扱い |
|---|---|---|
| `commonmark` | `True` | そのままHTMLとして通す |
| `default` / `zero` | `False` | `&lt;br&gt;` にエスケープ |

**`commonmark` プリセットを使うため、Markdown中の生HTMLはそのまま通る。**
Markdownに直接HTMLを書いて細かい装飾を効かせたい場合に有用なので、この挙動を採用する。
入力は利用者自身がコピーしたテキストであり、外部から受け取ったデータではないため、
サニタイズは行わない。

- どちらも `clipmd` 実行時のみ使うため**遅延インポート**にする
  （他コマンドの起動コストに影響させない）。
- 依存追加: `markdown-it-py`, `markdownify`。
- `markdown-it-py` は**既定（commonmarkプリセット）では表を段落として扱ってしまう**ため、
  `MarkdownIt("commonmark").enable("table")` で明示的に有効化する（検証済み）。

### HTML前処理パス（BeautifulSoup）

`markdownify` は変換中のフックを提供しないため、**変換の前にBeautifulSoupでHTMLを走査する
パスを設ける**。後述の表・画像に関する対処はすべてここで行う。

このパスが担うこと:

1. **書き換え** — セル結合の空セル補完、`<thead>` がない表の1行目をヘッダー化
2. **情報の収集** — 列の配置指定（`text-align`）、セル結合の有無、セル内のブロック要素・画像、
   `file:///` 参照、データURIのサイズ
3. **警告ログの出力** — 収集した情報のうち、変換で失われるものを利用者に知らせる

`beautifulsoup4` は `markdownify` の依存として既に入るため、追加の依存宣言は不要。
ただし直接importするため、`dependencies` に明示的に宣言する
（推移的依存に暗黙に頼るのは壊れやすい。`cwc` の `onnxruntime` と同じ方針）。

列の配置指定の復元だけは `markdownify` の出力後に区切り行を差し替える必要があるため、
**前処理で収集した配置情報を使って後処理で書き換える**という流れになる。

## 表（テーブル）の扱い

業務文書では表が頻出する一方、**MarkdownとHTMLの表現力の差が最も大きいのが表**である。
ライブラリ既定の挙動では実務上問題が出ることを検証で確認したため、以下の方針を取る。

### 表: Markdown → リッチテキスト

`enable("table")` を有効にすれば、GFM記法の表は `<table>` に正しく変換される。
列の配置指定（`|---:|` など）も `style="text-align:right"` として保持される（検証済み）。
この方向は概ね問題ない。

### 表: リッチテキスト → Markdown

Markdownの表には構造上の制約があり、**HTMLの表を完全には表現できない**。
以下の各ケースについて、明示的に対処する。

#### 1. `<thead>` がない表 → 1行目をヘッダーに昇格させる

WordやWebページの表は `<thead>` を持たないことが多い。`markdownify` の既定では
**空のヘッダー行が捏造され、本来の1行目がデータ行に落ちる**（検証済み）。

```text
入力: <tr><td>x</td><td>y</td></tr><tr><td>1</td><td>2</td></tr>
既定: |  |  |          ← 空ヘッダーが生える
      | --- | --- |
      | x | y |        ← 見出しのはずがデータ行に
      | 1 | 2 |
```

実際の表は1行目が見出しであることが多いため、**`<thead>` がない場合は1行目を
ヘッダー行として扱う**ように既定挙動を上書きする。

#### 2. セル結合（colspan / rowspan）→ 空セルで埋めて列数を揃える

Markdownの表はセル結合を表現できない。`markdownify` の既定では列数が合わず、
**以降の行とずれて表全体が崩れる**（検証済み）。

```text
入力: <td colspan="2">結合セル</td>
既定: | 結合セル | |   ← 列数が合わない
```

`colspan="2"` なら空セルを1つ追加するなど、**不足分を空セルで補って列数を揃える**。
表の見た目は保たれるが、結合されていたという情報は失われる。
セル結合を検出した場合はその旨をログに出す（意味が変わったことを利用者が追えるように）。

#### 3. セル内の複数行・ブロック要素 → 情報が失われることを許容する

Markdownの表のセルには改行やブロック要素を入れられない。以下は潰れる（検証済み）。

```text
<br>入り                        → 「改行 入り」（スペースに）
<p>段落</p><p>2つ</p>           → 「段落  2つ」（連結）
<ul><li>a</li><li>b</li></ul>   → 「* a * b」（リスト崩壊）
```

これはMarkdownの仕様上の限界であり、回避策はない。
**セル内にブロック要素があった場合は警告ログを出す**にとどめ、変換自体は続行する。

#### 4. 列の配置指定 → 往復では失われる

HTML側の `style="text-align:right"` を `markdownify` は読まないため、
`|---:|` は往復すると `| --- |` になる（検証済み）。

後述のHTML前処理パスで `<th>` / `<td>` の `text-align` を読み取り、
**区切り行の記法（`:---` / `:---:` / `---:`）を復元する**。
前処理でHTMLを走査する仕組みは他の対処（セル結合の補完など）でも必要になるため、
そこに相乗りさせる。

### まとめ: 表について守ること

- 変換自体は必ず完走させる（表があるだけでエラーにはしない）
- 情報が失われた場合は**必ずログに残す**（何が変わったか追えるようにする）
- Markdownで表現できないもの（セル結合、セル内改行）は割り切る

## 画像の扱い

**基本方針: 変換は忠実に行い、画像ファイルの生成・コピーなどの副作用は持たない。**
リンクが切れる、巨大な行になるといった問題は**警告ログで知らせるにとどめる**。
勝手にファイルを作らないというCLAUDE.mdの姿勢と揃える。

### 画像: Markdown → リッチテキスト

`![alt](url)` は `<img src alt>` に正しく変換される（検証済み）。この方向は問題ない。

- ローカルパスの画像（`![x](C:/path/to/a.png)`）はそのまま `src` に入る。
  貼り付け先がメールの場合、**受信者の環境では表示されない**旨を警告ログに出す。

### 画像: リッチテキスト → Markdown

#### 1. Word等からコピーした画像 → リンクは維持し、警告ログを出す

Wordは画像を `%TEMP%\msohtmlclip1\` に書き出して `file:///` で参照させる（検証済み）。

```text
本文![](file:///C:/Users/x/AppData/Local/Temp/msohtmlclip1/01/clip_image001.png)
```

この一時ファイルは**Wordを閉じるか時間が経つと消えるため、リンクは後から切れる**。

- リンクはそのまま維持する（画像ファイルの退避コピーはしない）
- `file:///` を含む画像参照を検出したら、
  **「一時ファイル参照のため後からリンクが切れる可能性がある」旨を警告ログに出す**
- 特に `msohtmlclip` を含むパスはWord由来の一時ファイルとして確度が高いため、
  ログで明示的に指摘する

利用者が画像を残したい場合は、貼り付け先で画像を別途保存する運用とする。

#### 2. base64データURI → そのまま埋め込む

```text
![埋め込み](data:image/png;base64,iVBORw0KGgo...)
```

データURIはそのままMarkdownに埋め込む（デコードしてファイル化はしない）。
変換の忠実性を優先し、画像データを失わないことを重視する。

- 実画像では**数十KB〜数MBの1行**になる。エディタが重くなる可能性があるため、
  データURIを検出したら**そのサイズを警告ログに出す**
  （何が起きたか分からないまま巨大な行が貼られるのを防ぐ）。

#### 3. 表のセル内の画像 → 消える

Markdownの表のセルには画像を置けないため、`markdownify` は `alt` テキストだけを残して
画像参照を落とす（検証済み）。

```text
<td><img src='x.png' alt='A'></td>  →  | A |
```

これはMarkdownの仕様上の限界。**セル内に画像があった場合は警告ログを出す**にとどめ、
変換自体は続行する。

#### 4. alt属性がない画像

`![](url)` となる（検証済み）。これはMarkdownとして正当なので、そのままとする。

### まとめ: 画像について守ること

- 画像ファイルの生成・コピー・削除は一切しない（副作用を持たない）
- リンク切れの危険、巨大なデータURI、消えた画像は**すべて警告ログで知らせる**
- 画像があるだけでエラーにはしない

## リッチテキスト側で使うHTMLの体裁

Outlook/Wordに貼ったときに崩れにくくするための方針。

- **CSSクラスは使わず、インラインスタイルのみ**にする
  （クリップボード経由では外部CSSも`<style>`も無視されるアプリが多い）。
- フォント指定は行わない（貼り付け先のスタイルに従うのが望ましい）。
- コードブロックは `<pre>` に等幅フォントのインラインスタイルを当てる。
- 変換後のHTMLをそのまま使い、独自の見た目調整は最小限にとどめる
  （凝った整形はアプリ側で崩れるだけなので割に合わない）。

## エラー処理

- クリップボードに `CF_HTML` も `CF_UNICODETEXT` もない場合:
  「変換できるテキストがありません」と明示してエラー終了する。
- 変換結果が空文字列になった場合もエラー終了する
  （空をクリップボードに書き込むと、元の内容を失うだけで害しかない）。
- クリップボードのオープンに失敗した場合（他プロセスがロックしている）は、
  その旨を明示したエラーにする。短時間のリトライは行うが、無限に粘ることはしない。

## 依存追加まとめ

```toml
dependencies = [
    ...,
    "markdown-it-py>=3",   # Markdown → HTML、遅延インポート
    "markdownify>=0.13",   # HTML → Markdown、遅延インポート
    "beautifulsoup4>=4.12", # HTML前処理パス用、遅延インポート
                            # （markdownifyの依存として入るが直接使うので明示）

```

いずれも `clipmd` 実行時のみ読み込む。他コマンドの起動コストには影響しない。

## セキュリティ方針との整合（CLAUDE.md）

- クリップボードの読み書きは `win32clipboard` の公開API
  （`OpenClipboard`/`GetClipboardData`/`SetClipboardData`）のみを使う。
  グローバルフックや常駐監視は行わない。
- **コマンドを実行したその場で1回だけ読み書きする**。バックグラウンドでの監視はしない。
- 外部通信は一切発生しない（変換はすべてローカル処理）。
- 何をどちらの向きに変換したかをログに出し、挙動が不透明にならないようにする。

## テスト方針

`tests/processing/test_clipmd.py` に以下を用意する。
クリップボードAPIは `monkeypatch` でモックし、実際のクリップボードは触らない。

### 変換方向の判定

- `CF_HTML` がある場合に HTML→Markdown が選ばれること
- `CF_UNICODETEXT` のみの場合に Markdown→リッチテキスト が選ばれること
- どちらもない場合にエラー終了すること
- `--to-markdown` / `--to-rich` が自動判別を上書きすること
- `--to-markdown` 指定で `CF_HTML` が無い場合、
  `CF_UNICODETEXT` をHTMLソースとして解釈すること
- `--to-rich` 指定で `CF_HTML` がある場合、
  `CF_HTML` を無視して `CF_UNICODETEXT` をMarkdownとして解釈すること
- オプションで自動判別と異なる解釈をしたとき、その旨がログに出ること

### CF_HTML の組み立て・解析

- 書き込んだ `CF_HTML` のヘッダオフセットが、実際のバイト位置と一致すること
  （`StartFragment`/`EndFragment` の位置に本当にマーカーがあることを検証する）
- `<!--StartFragment-->`〜`<!--EndFragment-->` から断片を取り出せること
- ヘッダのオフセットが壊れていても、コメントマーカーから復元できること
- `GetClipboardData` が bytes を返す場合と str を返す場合の両方を扱えること

### 変換内容

- Markdown → HTML: 見出し・太字・箇条書き・リンク・表・コードブロックが変換されること
- HTML → Markdown: 上記が逆向きに復元されること

### 表

- Markdown → HTML: GFM記法の表が `<table>` になること
  （`enable("table")` を忘れると段落になるため、退行検知として重要）
- Markdown → HTML: 列の配置指定 `|---:|` が `text-align` として保持されること
- HTML → Markdown: `<thead>` のある表が正しくヘッダー付きで変換されること
- HTML → Markdown: **`<thead>` のない表で、1行目がヘッダーに昇格すること**
  （空ヘッダー行が生えないこと）
- HTML → Markdown: **`colspan` を含む表で、空セルが補われて全行の列数が揃うこと**
- HTML → Markdown: セル結合を検出したとき警告ログが出ること
- HTML → Markdown: セル内にブロック要素（`<p>`/`<ul>`/`<br>`）があるとき警告ログが出ること
- 表を含む変換がエラーにならず完走すること

### 画像

- Markdown → HTML: `![alt](url)` が `<img src alt>` になること
- HTML → Markdown: `<img>` が `![alt](url)` に戻ること
- HTML → Markdown: **`file:///` を含む画像参照で警告ログが出ること**
  （`msohtmlclip` を含む場合はWord由来として明示されること）
- HTML → Markdown: **base64データURIがそのまま維持され、サイズが警告ログに出ること**
- HTML → Markdown: 表のセル内に画像があるとき警告ログが出ること
- `alt` がない画像が `![](url)` になること
- **画像に関するどの処理でも、画像ファイルを新規作成しないこと**
  （副作用を持たない方針の退行検知。`Path.write_bytes` / `open` を
  monkeypatchで監視し、書き込みが発生しないことを確認する）
- 画像を含む変換がエラーにならず完走すること

### クリップボードへの書き戻し

- Markdown→リッチ変換時に `CF_HTML` と `CF_UNICODETEXT` の両方がセットされること、
  かつ `CF_UNICODETEXT` には元のMarkdownがそのまま入ること
- リッチ→Markdown変換時に `CF_UNICODETEXT` のみがセットされること
  （`CF_HTML` がセットされないこと）
- 2形式のセットが**1回の `OpenClipboard` セッション内**で行われること
  （`EmptyClipboard` が2回呼ばれて先にセットした形式が消えないこと）

### エラー

- 変換結果が空になる入力でエラー終了すること
